# F52 CSV export — execution plan

**Global source:** `PLAN.md` F52, sections 4.3, 8.1, 9.2, 10, 14, and 18. **Behavior contract:** `docs/superpowers/specs/2026-10-07-f52-csv-export-design.md`.

## Task 1: Versioned Excel-compatible CSV writer

1. Add Go golden tests first for BOM, semicolon, exact Russian column order, date formatting, quoted delimiters/newlines, formula-like text, and unchanged amount; observe RED.
2. Implement `csv-v1` as a streaming writer in a focused Go package. Do not change the legacy serializer or route Telegram through the new exporter.
3. Run focused export tests, the full Go suite, `go vet`, and contract checks.

## Task 2: Durable Core export request/status and authorization

1. **Task 2a — request/status slice (in progress):** PostgreSQL/API tests for owner/member scope, range bounds, 100,000-row rejection, cross-tenant/member denial, atomic job/outbox, status audit, BFF routes, and no finance writes. The request captures posted rows within a repeatable-read transaction. Later edits cannot change the snapshot.
2. Add worker-only claim/read/page/complete/fail APIs in Task 2b. Authorize every page by export ID; prevent arbitrary tenant scans. Add API tests first.
3. Run focused PostgreSQL/API/contract tests and full Core checks; commit verified Task 2a independently before starting Task 2b.

## Task 3: Bounded Go export worker and private object download

1. Add worker tests first for page ordering, snapshot bound, retry/idempotency, max rows, interrupted stream, partial-object cleanup, and completion only after storage success; observe RED.
2. Implement the `jobs.export.v1` consumer with bounded concurrency, keyset streaming, the Task 1 writer, and private S3-compatible storage.
3. Add Core-owned short-lived signed URL generation after job authorization. Test ready/failed/expired/cross-tenant cases; never persist or log the signed URL.
4. Run Go tests/vet plus storage integration tests where local S3-compatible test infrastructure exists.

## Task 4: Web export flow

1. Add Web tests first for filters, role-based member scope, job progress, empty export, retryable failure, and download; observe RED.
2. Add `/exports` RU/EN screen and typed API calls. Show the selected period/member, job state, and available download action.
3. Run Web tests and production build.

## Task 5: Regression and F52 completion

1. Run Core/PostgreSQL, all contracts/migrations, Go, Web, and `git diff --check`.
2. Verify existing transaction filters and finance totals remain unchanged. Record evidence in `.agent/PROGRESS.md`.
3. Commit/push the verified slices. Mark F52 complete only when all code acceptance criteria pass. Record live S3 deployment separately if no real storage endpoint is available.

## Execution constraints

- Work in strict `PLAN → ACCEPTANCE → TESTS → OBSERVED RED → IMPLEMENT → GREEN → REGRESSION → VERIFY → COMMIT → PROGRESS` order.
- Keep owner/member scope enforced in Core; UI scope is not authorization.
- Preserve user-owned untracked paths. Stage only F52 files.
