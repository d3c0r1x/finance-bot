# Личный MVP Finance Bot V1

Обновлено: 2026-10-11. Этот документ дополняет `PLAN.md` и не заменяет F01–F60.

## Цель

Подготовить минимально пригодный V1 для личного использования за ограниченный пользователем цикл около 1,5 часа: надёжно запускаемый backend на ПК пользователя, доступный с телефона через публичный HTTPS, и устанавливаемое Android-приложение с полным RU/EN каркасом согласованных возможностей.

Временной лимит не меняет критерии приёмки. Если критическая внешняя зависимость отсутствует, честный результат — частично готовый локальный MVP с конкретным BLOCKED-условием. Нельзя называть такой результат публично доступным или полностью запущенным.

## Зафиксированные решения

| Область | Решение |
|---|---|
| Сервер | ПК пользователя; пользователь готов держать его включённым и подключённым к Интернету |
| Публичный доступ | Нужен публичный HTTPS-адрес; Tailscale не подходит по выбору пользователя. Не менять DNS/NS, firewall или роутер, пока не подтверждены права на домен и текущие записи. Публичный ingress включать лишь после защищённого runtime и проверки извне |
| Android | Минимум API 23; проверка доступными эмуляторами Android 6–8 |
| Identity | Keycloak + OIDC; открытая регистрация email/пароль, проверка email и восстановление доступа |
| Email | Провайдера ещё нет; для живой проверки нужен реально работающий sender и домен. Не ослаблять verification ради локального зелёного теста |
| Функции | Полный набор экранов/переходов V1; доступные действия используют API. Нереализованные backend-сценарии явно показывают недоступность |
| Git | Каждая завершённая цель — отдельный проверенный commit; push разрешён ранее данным пользователем поручением коммитить в GitHub. Не включать пользовательские локальные файлы и секреты |
| V2 | Не выполнять и не планировать как текущую цель до завершения V1 |

## Этапы и критерии приёмки

### M0. Установить реальное состояние окружения

- Проверить ветку, HEAD, dirty diff и уже работающие процессы; сохранить пользовательские данные.
- Зафиксировать доступные эмуляторы и версии Android, наличие SDK/JDK/runtime, БД, Keycloak и способ запуска.
- Проверить, какие сервисы уже живы. Не считать экран Cloudflare Build доказательством работающего backend.
- Результат: список фактов и отсутствующих зависимостей с командами/проверками в `.agent/PROGRESS.md`.

### M1. Android MVP на API 23+

- **M1.1 совместимость API 23 — COMPLETE:** сборка объявляет `minSdk 23`; core library desugaring поддерживает `java.time` на Android 6. Полный instrumentation suite проходит на Android 6/API 23, Android 7.1/API 25 и Android 8.1/API 27.
- **M1.2 адреса окружений и release-защита — CODE COMPLETE:** `-PfinanceApiBaseUrl=...` и `-PfinanceOidcIssuer=...` попадают в BuildConfig; release блокируется без HTTPS адресов и отклоняет loopback/private IP. Debug сохраняет адреса эмулятора. Сборка релизного APK для телефона ожидает реальный URL из M2/M3.
- URL Core API и OIDC issuer задаются build config/environment, debug локальные значения отделены от production HTTPS.
- Тесты доказывают корректность выбора debug/release endpoints, HTTPS ограничения для release и сериализацию важного текущего user flow.
- Сначала запустить тесты и наблюдать ожидаемый RED для текущего несоответствия. Для M1.1 это было `minSdk 26` и отсутствие `java.time` на API 23; после исправлений получить GREEN, собрать debug APK и установить/запустить на API 23, 25 и 27.
- Не использовать API 34 эмулятор как единственное доказательство поддержки Android 6–8.
- Пройти экраны входа/регистрации, главные разделы V1, состояния загрузки/ошибки/пустых данных. Не маскировать отсутствие сервера фиктивными финансовыми данными.

### M2. Повторяемый runtime на ПК

- Определить минимальный поддерживаемый состав сервисов из текущего репозитория; не добавлять платные/облачные зависимости без необходимости.
- Сервисы стартуют штатной командой из чистого checkout, сохраняют данные после рестарта и восстанавливаются после падения.
- Настроить безопасный автозапуск backend после reboot и перезапуск после изменений только после зелёной проверки затронутых тестов.
- Проверить health/readiness, сохранность данных после restart, остановку/повторный запуск. Не менять sleep, firewall, роутер или DNS без необходимой причины.
- Если Postgres/Keycloak или иной обязательный runtime отсутствует, установить blocker и продолжить независимую работу; не сообщать, что сервер работает all-time.

**Проверка M2 (2026-10-06, историческая):** runtime не был установлен; PostgreSQL на `127.0.0.1:55438` был временным тестовым процессом, не долговечной базой. Не создавать постоянную службу на его основе.

**Повторная проверка M2 (2026-10-11):** Docker, Podman, WSL-дистрибутив, Keycloak, `cloudflared` и локальные API/БД сервисы не обнаружены; проверенные backend, PostgreSQL, Kafka, ClickHouse, Keycloak и S3 порты не слушаются. Tailscale установлен, но пользователь выбрал публичный HTTPS без него; Funnel не настраивать. Java доступна внутри Unity Android JDK, но отсутствует в `PATH`. В репозитории нет полного Compose/Wrangler runtime. Скриншот Cloudflare подтверждает только запуск Worker-сборки из GitHub на `main` с корнем `/` и командой `npx wrangler deploy`; он не подтверждает Java Core, постоянную БД, Keycloak, регистрацию или readiness текущей ветки. M2 остаётся BLOCKED; система и сеть не менялись. Следующее действие: выбрать безопасный поддерживаемый runtime и зафиксировать способ постоянного хранения; до проверки OIDC/auth публичный backend не открывать.

**M2.1 (2026-10-12):** добавлен локальный Compose-профиль Core/PostgreSQL/Keycloak, импорт realm, loopback-only host ports, persistent volumes и restart policies. Core использует отдельную роль `finance_app` с DML grants; Flyway запускается ролью `finance_migrator`, владеющей schema, без предоставления этой роли приложению. Пароли init SQL читает через `psql \\getenv`, не передавая в argv. DB name зафиксировано как `finance`, чтобы JDBC и init SQL не расходились. Core issuer совпадает с внутренним Keycloak hostname; это нужно заменить единым публичным HTTPS issuer прежде чем включать клиентский login. Healthcheck Keycloak использует заранее скомпилированный Java probe, поскольку официальный образ исключает curl и compiler support не гарантирован. Первая acceptance-проверка была RED (3 недостающих требования); отдельная регрессия обнаружила передачу паролей через argv, после исправления GREEN. `.venv\Scripts\python.exe -m pytest -p no:cacheprovider -q tests/test_compose_core_bootstrap.py` — 6 passed; `:services:core:test :services:core:bootJar` — 292 Core tests, 0 failures/errors, сборка успешна; `bash -n` для init script, Java health probe compile, YAML/realm JSON parse и `git diff --check` успешны. Java вызвана напрямую из уже установленного Unity Android JDK без изменения системного PATH.

M2 остаётся **PARTIAL / NOT RUN**: Docker/Podman CLI недоступны, поэтому Compose interpolation, PostgreSQL role/bootstrap SQL, Keycloak image/import/readiness, контейнерная сборка, реальные рестарты и сохранность volume не запускались. Dev Keycloak не является production-конфигурацией. Core и Keycloak опубликованы только на `127.0.0.1`; внешний доступ, SMTP/email verification и постоянный автозапуск ОС не настроены. Следующий шаг — после появления поддерживаемого контейнерного runtime выполнить чистый запуск, миграции, health/restart/persistence проверки и локальный OIDC flow; M3 остаётся закрыт до верификации домена и безопасного публичного маршрута.

### M3. Публичный HTTPS и защита

- Обеспечить публичный HTTPS адрес без port forwarding и без Tailscale; провайдера/домен и реальный адрес определить после подтверждения доступного runtime.
- Public routing exposes only the needed web/API ingress. Database, admin consoles, Keycloak admin and internal worker endpoints are not published.
- Проверить TLS, OIDC login, tenant isolation, неавторизованный отказ, health route без раскрытия секретов и безопасные response headers.
- Не включать public route, пока auth не защищает финансовые маршруты.
- Cloudflare Worker из предоставленного screenshot пока не заменяет backend. Не менять DNS/NS до проверки владельца зоны и сохранения действующих web/mail записей.

### M4. Полный auth/email flow

- Открытая регистрация, email verification, повторное письмо, логин, logout, восстановление пароля и отказ до верификации.
- Интеграционные тесты подтверждают токены OIDC и отказ неактивной/неподтверждённой учётной записи на API.
- Тестовое письмо должно быть реально перехватываемым локальным mail sink для автоматических проверок; production delivery проверяется реальным sender.
- Пока sender/domain не настроен и не проверен, production email verification — BLOCKED. Не подменять письма логом или UI-сообщением.

### M5. End-to-end MVP gate

- Чистая установка APK на поддерживаемый Android emulator/device.
- Создать пользователя, пройти email verification, войти, создать и прочитать финансовую запись, закрыть/открыть приложение и увидеть сохранённые сервером данные.
- Проверить доступ с публичного HTTPS адреса; затем перезапустить backend и подтвердить возврат readiness и сохранность данных.
- Проверить Android release config не содержит emulator `localhost`/`10.0.2.2`, debug HTTP не попал в release, финансовый API требует OIDC.
- Сохранить APK, SHA-256, URL (без секретов), commit, результаты тестов и ограничения в `.agent/PROGRESS.md`.

### M6. Продолжить F01–F60 до полного V1

- После MVP gate выбрать первую незавершённую цель из `.agent/PROGRESS.md` и parity registry.
- Для каждой функции продолжить test → observed RED → code → GREEN → regression → verification → commit → progress.
- Не трактовать личный MVP как завершение full parity, миграции, production SaaS, billing или F01–F60.
- После полного V1 остановиться на итоговой проверке. V2 не начинать без нового явного поручения пользователя.

- Следующее действие: подготовить реалистичный план запуска runtime и проверку постоянства данных. Если выбранный поддерживаемый runtime требует включения системных функций или перезагрузки, сначала подтвердить обратимость изменений и отсутствие влияния на сетевые настройки ПК.

## Общие эксплуатационные ограничения

- «Всегда работает» означает автозапуск и восстановление процессов на работающем ПК с питанием и Интернетом. Выключенный ПК или отключённый Интернет недоступность не устраняет.
- Любой внешний HTTPS tunnel делает ingress доступным из Интернета. Держать за ним только защищённое приложение; никаких открытых финансовых API.
- Секреты хранить вне Git, создать rotate/backup процедуру. Перед commit проверять staged diff и секреты.
- Изменение production процесса: тесты → успешная сборка → перезапуск сервиса → readiness → smoke test. При провале не объявлять обновление активным.
