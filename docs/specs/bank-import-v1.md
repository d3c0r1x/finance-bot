# Bank statement import v1

This flow accepts the supported T-Bank PDF statement and stages a versioned preview. The original PDF is sent to the private parser in memory and is not stored as a document. Core persists the parsed statement rows, parser version, reconciliation status and explicit row choices under the current tenant and importing member.

`POST /bff/tenants/{tenantId}/imports` and the equivalent authenticated Core API accept one PDF file up to 12 MiB. The parser endpoint is internal and service-token protected. Parser output is validated against `tbank-statement-result.v1` before staging. A malformed, scanned, unsupported or unreadable PDF returns a safe explanatory error without creating a staged import.

The initial policy includes negative purchases as expenses, positive income as income and positive refunds as refunds. Fees, transfers, cash withdrawals and internal transfers remain excluded by default. Every excluded row appears with its signed amount and reason. A member can select expense, income, refund or transfer for a row; sign rules still apply to expenses, income and refunds. `null` restores the default decision. `BigDecimal` recomputes every included and excluded total; no row is silently dropped.

Statement quality remains exactly `valid`, `mismatch` or `unverifiable`. Missing bank totals remain null, and a preview never upgrades quality. The Web view displays parsed totals alongside bank totals when they differ or cannot be checked.

Preview edits require the current quoted `If-Match` revision. Each successful edit advances the revision; stale edits return `412`. Staged rows do not create transactions. Confirmation requires `{ "confirmed": true }`, the current quoted `If-Match` revision and an `Idempotency-Key`; it creates transactions and outbox events in one database transaction. Repeating the same confirmation key returns the committed batch without inserting rows again.

Before confirmation the preview checks import-origin dedupe keys and marks matches. The canonical SHA-256 input is tenant, card-last-four account discriminator (or `unknown-account`), operation date/time, currency, signed amount and the full NFKC-normalized, lowercased, whitespace-collapsed description. A one-based occurrence number separates identical operations in the same ordered statement, so two identical purchases in one statement create two transactions. Unique tenant/fingerprint/occurrence keys serialize overlapping imports; the losing batch records the row as a duplicate and links the existing transaction. Manual and receipt-origin transactions do not match bank-import keys.

Confirmation atomically stores each included row as created or duplicate, excludes all other rows, records batch counts and audit data, and writes a standard `transaction.created` outbox event for every inserted transaction. The idempotency keys, batch rows and dedupe registry are tenant-scoped. Undo requires the current batch revision and an idempotency key. It voids only transactions linked as created by that batch and only when each still has its original version, posted state, owner and `bank_import` source. If any row changed, undo returns the conflicting transaction IDs with HTTP `409` and leaves the entire batch committed; it does not partially cancel the batch. A successful undo voids the batch's own rows atomically and releases only its dedupe keys, so the statement can be imported again deliberately.

Merchant category rules, AI hypotheses, per-member cache, the six-item clarification limit and the 300 RUB threshold follow [merchant-classification-v1.md](merchant-classification-v1.md). F50 suggestions remain hypotheses until a member selects a category. That choice persists as a personal merchant mapping. F51 separately handles explicit reclassification of already posted imports.
