# F43 — потолок необязательных покупок, недельный тренд и наблюдение после совета

Статус: спецификация одобрена пользователем 2026-10-07 сообщением «Делай»; реализация начнётся после ревью пошагового плана.

## Цель и границы

Перенести три существующих расчёта из `services/advice.py` в SaaS-аналитику: месячный потолок по необязательным покупкам, долю необязательного по неделям и изменение частоты покупок после первого совета. Результаты описывают чеки и совпадение по времени. Они не доказывают экономию и причинный эффект совета.

Сохранить границы источника: текущий активный участник, только подтверждённые расходы и позиции чеков; решения участника `allowed` исключают товар из потолка. Семейный агрегат и сырые описания транзакций не входят в F43.

## Одобренное поведение

- Потолок: последние 90 дней; считать только привычные группы с минимум двумя подходящими позициями и вердиктом `harmful`/`unnecessary`; исключить разрешённые товары. Пересчёт темпа — `сумма / 90 × 30`; доход и месячный лимит, если заданы, показывать только как необязательный масштаб. Подписывать результат как теоретический потолок, не фактическую или гарантированную экономию.
- Тренд: четыре скользящие семидневные корзины в часовом поясе участника. Знаменатель — сумма всех подтверждённых разобранных позиций с известной суммой; неизвестный verdict остаётся только в знаменателе, не становится neutral evidence. Долю строить по сумме, не по числу позиций. Пустую неделю пропускать. Без двух недель с данными тренд недоступен, а не равен нулю. Если сумма отсутствует, вернуть partial/unavailable reason; не подставлять ноль.
- Эффект: выбрать первую датированную позицию с `harmful`/`unnecessary` как срез совета. Требовать минимум две покупки того же нормализованного товара до среза. Если прошло меньше 21 дня, вернуть `pending`; иначе сравнить частоту до и после по интервалам, включая ноль покупок после. Изменение называют «реже/чаще» только при сдвиге темпа более 20%; меньший сдвиг — «так же часто». Текст явно говорит, что это наблюдение, а не доказательство причинности.
- Пересчёт verdict по F42 не считается новой покупкой или эффектом совета. Отчёт отделяет сумму изменения классификации от денежного тренда и помечает окно, где вердикты были пересчитаны.

Числа, округление, нормализация товара, пороги, 5/4/10 top limits, шум тренда 5 процентных пунктов и отсутствие данных должны совпасть с fixtures и утверждёнными legacy-поведенческими тестами. Денежные суммы передавать и считать десятичным типом; не использовать binary float.

## Владение данными и поток

1. Core проверяет активную membership и роль, затем фиксирует ограниченный snapshot личных чековых позиций, покупок до/после совета, `allowed` решений, профильных лимита/дохода, часового пояса и записей F42. Snapshot имеет монотонный `inputWatermark`; выборка превышает лимит на одну строку и явно возвращает `too_many_items` вместо усечённого результата.
2. Core создаёт или переиспользует durable recompute job для пары участник + watermark + версия алгоритма. Повтор одинакового ключа идемпотентен; новая версия входа не перезаписывается запоздалой старой задачей.
3. Go analytics worker получает минимальный внутренний payload, вычисляет F43 и сохраняет небольшой результат через J result API. Снимок включает watermark, версию алгоритма и `complete`/`partial` статус. Задача имеет lease, ограниченные попытки и повторное выполнение.
4. Web/J query API возвращает job state (`pending`, `processing`, `ready`, `failed`, `stale`), watermark и расчёты. UI показывает статус и причину отсутствия метрики; не показывает устаревший результат как свежий. При `stale` пользователь может запросить актуальный пересчёт.

Переиспользовать существующий outbox/job, Kafka и worker lifecycle, если они подходят после проверки кода. Не добавлять отдельный deployable ради F43. Производный маленький отчёт хранить через result API; ClickHouse использовать только для подходящих тяжёлых проекций. Никакой публичный endpoint Go не открывается; Core остаётся владельцем доступа и данных.

## Проверяемая приёмка

- Go golden tests совпадают с legacy fixtures для потолка, пустых недель, тренда, раннего ожидания, уменьшившейся/неизменной/выросшей частоты, разрешённого товара и F42-пересчёта.
- Тесты доказывают, что одна покупка не создаёт потолок; разрешённый товар исключён; менее двух недель не выдаёт нулевой тренд; меньше двух прежних покупок не выдаёт эффект; до 21 дня выводится pending; ноль последующих покупок не называется доказанной экономией.
- Core PostgreSQL tests доказывают owner/member isolation, watermark, идемпотентную постановку, повтор job, защиту от перезаписи свежего результата старой задачей, lease/retry и overflow без усечения.
- Web показывает только результат текущего watermark, обновляет статус после poll и локализует недоступные данные. Telegram-отчёт использует тот же Core DTO, если текущий маршрут отчётов позволяет показать его без второго расчёта.
- Контракт фиксирует API, внутренний Go payload и причины `insufficient_history`, `missing_amounts`, `too_many_items`, `analytics_unavailable`.
- Финансовые транзакции и суммы чеков не изменяются.

## За рамками

Не оценивать сэкономленную сумму как факт; не приписывать изменение совету; не менять советы или блокировки автоматически; не включать прогнозы и покупки без подтверждённых фактов; не выполнять dual-write между PostgreSQL и ClickHouse.
